# GIF 动图分镜插件（maibot-plugin-gif-storyboard）

给 MaiBot（麦麦）补一块"动图视力"：**在 GIF 动图交给视觉模型之前，把动画的各个帧合成到同一张图上**，让视觉模型能看到动画的内容与时序——而不是只看到第一帧。

全部通过插件 SDK 实现，**不改宿主一行代码**。

- 插件 ID：`github.elmeir.gif-storyboard`
- 宿主要求：MaiBot ≥ 1.2.4（maibot-plugin-sdk ≥ 2.0）
- 依赖：Pillow ≥ 10.0.0（自动安装）
- 作者：[Elmeir](https://github.com/Elmeir) ｜ License：MIT
- 版本：见 [_manifest.json](_manifest.json)，变更见 [CHANGELOG.md](CHANGELOG.md)

## 为什么需要它

麦麦收到图片后会调用视觉模型（VLM）生成描述。VLM 链路是：

```
消息组件 binary_data ──► ImageManager.get_image_description(image_bytes)
                        ──► base64 + image_format ──► vlm.generate_response_for_image(...)
```

GIF 原样进入这条链路时，**大多数视觉模型对 `image/gif` 只取第一帧**：一个 20 帧的摔跤动图，麦麦眼里永远只有"开局那一瞬"。本插件在链路更早的位置把各帧拼成一张网格图（每帧带序号），VLM 看到的就变成了完整的"分镜表"。

## 工作原理

- 订阅宿主 `chat.receive.before_process` 钩子（消息进入处理链**之前**，允许改写）；
- 对消息里 `image` / `emoji` 组件的 `binary_data_base64` 检测 GIF 魔数（`GIF87a` / `GIF89a`）；
- 命中动图时用 Pillow 解帧 → **按时序均匀抽样**（默认最多 9 帧 = 3×3 网格）→ 拼成白底网格图（每帧左上角画序号）；
- **替换 + 落库前恢复（普通图片 GIF）**：组件二进制与 hash 暂时替换为合成图，原图字节暂存内存——宿主 `process()` 识别的就是多帧网格图，多帧描述成为该图的**第一份描述**（没有首帧描述，也就没有固化竞态）；`chat.receive.after_process` 钩子在消息落库**之前**恢复原图组件，图片文件、记录、WebUI 展示全部按原图保真；
- **表情包 bypass**：原表情组件原样保留，另追加携带合成图的隐藏组件参与识别（表情库保真），识别完成后回收；
- 搬运任务把多帧描述写入原图 hash 的 Images 记录，宿主视觉占位刷新器（`chat_history_refresher`）自动回填进麦麦上下文——由于原图记录从不参与宿主识别，回填的必然是多帧描述；
- **重复 GIF 快速路径**：同图重发时合成字节确定、hash 一致，插件直接把已就绪的多帧描述写入组件文本，宿主跳过识别，麦麦**零延迟**看到完整分镜；
- 全程只操作 Images 表数据与消息组件，**不改宿主一行代码**。

```
适配器上报消息 ──► [本插件] 组件替换为合成图 ──► 宿主 process（VLM 识别多帧，content 保持占位）
   ──► [本插件] after_process 恢复原图组件 ──► 消息落库（原图保真）
   ──► 后台把多帧描述搬到原图 hash 名下 ──► 刷新器回填 ──► 麦麦看到完整分镜
```

> 描述搬运依赖宿主 `database.query` 能力，已在 `_manifest.json` 的 `capabilities` 中声明。
> 若日志出现"database.query 能力不可用"，说明插件版本过旧或 manifest 被改动——此时
> 合成图仍会被识别，但描述无法回填，视觉上会退化为 GIF 首帧。

单帧 GIF（等价静态图）直接放行；解码失败、合成异常一律原样放行，绝不阻塞消息链。合成结果按「原图哈希 + 参数指纹」做内存缓存，同一个 GIF 反复刷屏也不会重复解码。

## 安装

```bash
cd /你的部署目录/plugins        # 例如 /opt/MaiBot/plugins
git clone https://github.com/Elmeir/maibot-plugin-gif-storyboard.git
# 重启麦麦（systemctl restart xxx / docker compose restart / 重启 bot.py）
```

> 目录名保持 `maibot-plugin-gif-storyboard`：插件配置存在插件目录内的 `config.toml`，换目录名会丢配置。

依赖只有 Pillow（`Pillow>=10.0.0`，见 requirements.txt；宿主环境一般已自带）。

重启后在 WebUI 插件页找到「GIF 动图分镜（视觉增强）」确认已启用。所有配置项都在插件面板里，均有中文标签与说明，通常保持默认即可。

## 配置说明

### [merge] 帧合成

| 配置项 | 默认 | 说明 |
|---|---|---|
| 处理图片 | 开 | 处理普通图片组件（`type=image`）中的 GIF（群友发的 GIF 动图主要走这里） |
| 表情包策略 | **bypass** | 见下表，三种策略任选 |
| 最多帧数 | 9 | 超出上限的动画按时序均匀抽样（含首尾帧）；9 = 3×3 网格。帧越多信息越全，但图更大、token 更贵 |
| 最少帧数 | 2 | 帧数不足视为静态图，原样放行 |
| 自适应帧数 | 开 | 按动画运动量自动在最少~最多帧数之间调节实际抽帧数：简单循环动画少抽（省 token），动作丰富、帧数多的多抽（保证证据）；调节结果记录在日志 |
| 绘制帧序号 | 开 | 每帧左上角标 1、2、3…，帮助 VLM 理解播放顺序 |
| 落库前恢复原图 | 开 | 识别完成后把替换组件恢复为原图、回收表情 ghost，防止合成图进入聊天记录/WebUI |

### 表情包策略怎么选

宿主表情链路"识别与存储共用同一个字节流"——直接替换表情二进制，`emoji_manager` 就会把合成图落盘表情库（`data/emoji`）并可能被收藏发出。因此提供三种策略：

| 策略 | 表情库存储 | VLM 识别 | 代价 |
|---|---|---|---|
| `bypass`（默认，推荐） | **原始 GIF**，收藏/发送完全保真 | 通过追加的合成图组件**看全多帧** | 表情 GIF 会多一次 VLM 调用（原图首帧 + 合成图各一次）；消息里多一个隐藏合成图组件 |
| `replace` | 合成图会进表情库、可能被收藏发出（观感是九宫格拼图），**原始 GIF 丢失** | 最直接 | 表情库污染 |
| `off` | 原始 GIF | 宿主原生行为（GIF 取首帧） | 识别退化 |

bypass 的效果：原表情组件原样保留，插件在其后追加一个 `content` 为空的 `image` 组件（携带合成网格图）。视觉链路照常走图片描述（落 `data/images`，不碰表情库），麦麦的上下文里会同时出现 `[表情包]` 与 `[图片: 动画各帧描述]`——既知道"这是个表情"，又知道动画内容。

## 只处理 GIF

插件只按文件头魔数（`GIF87a` / `GIF89a`）识别 GIF 动图：PNG / JPEG / WebP 等其他格式**零接触**；单帧 GIF 等价静态图，同样原样放行。

## 存储影响（重要）

| 存储位置 | 写入链路 | 默认行为 |
|---|---|---|
| 消息记录 / WebUI | 消息组件列表 | 替换组件在落库前恢复为原图，**聊天记录里只有原图/原表情**（表情 bypass 的 ghost 被回收） |
| `data/images`（图片识别缓存，Images 表 IMAGE 类型） | 图片组件（含追加的合成图组件） | 合成网格图会作为一次识别缓存落库（仅供 VLM 描述用途），原图照常落库 |
| `data/emoji`（表情库，Images 表 EMOJI 类型） | 表情包组件 | bypass / off 下**只落原始 GIF**，收藏与发送保真；`replace` 下会存进合成图 |

### [output] 输出图像

| 配置项 | 默认 | 说明 |
|---|---|---|
| 输出格式 | jpeg | jpeg 体积小省 token（推荐）；png 无损但明显更大 |
| JPEG 质量 | 85 | 50~95，仅 jpeg 生效 |
| 单帧格子边长上限 | 480 | 帧原图超过该尺寸等比缩小，控制合成图总体积 |
| 帧间隔（像素） | 4 | 网格帧之间的白色间隔 |

### [plugin]

| 配置项 | 默认 | 说明 |
|---|---|---|
| 插件总开关 | 开 | 关闭后 GIF 一律原样交给视觉模型 |

## 边界与说明

- **多帧描述有延迟**：合成图由宿主后台异步识别，搬运完成前该图在麦麦上下文中是空占位（planner 会按配置等待一段时间），搬运完成后刷新器自动回填完整多帧描述；同图再次出现时走快速路径零延迟。
- **识别窗口内的短暂替换**：从 `process` 到 `after_process`（通常亚秒级）组件携带的是合成图；此窗口内若进程崩溃，消息会以合成图形态落库（概率极低，日志有 warning）。
- **与消息防抖插件共存**：本插件的入站钩子挂在 `LATE` 槽位，处理的是防抖插件（`NORMAL` 槽，窗口期合并消息）放行后的最终消息——防抖窗口内并入的多条消息里的 GIF 也会被分镜处理。搬运日志会明确标注成功与否，便于排查。
- **bypass 的 token 开销**：表情包 GIF 会产生两次识别（宿主对原图的首帧描述 + 插件合成图的多帧描述），表情包场景频率有限，通常可接受；介意可改 `off`。
- **合并转发里嵌套的图片暂不处理**：仅处理消息顶层组件。
- **不改动组件 `data` 字段**：宿主以 content 非空判定"已识别过"，本插件只动二进制与 hash，不会干扰识别流程。
- **描述搬运依赖 `database.query` 能力**：见"工作原理"一节；能力缺失时插件会在加载日志里给出 warning。
- 典型开销：9 帧 480px 合成图 JPEG 约 100~300KB，单次合成毫秒级，缓存命中为零开销。

## 本地自检（可选）

```bash
pip install Pillow
python self_test.py
```

脚本会用 mock 的 SDK 环境（假 logger/db）加载插件，覆盖：多帧 GIF 合成、组件替换与恢复、单帧/非 GIF 放行、缓存命中、钩子改写路径、表情旁路 ghost 回收、描述搬运（正常 / 等待落库 / 超时告警）、重复 GIF 快速路径、`database.query` 故障告警等。
