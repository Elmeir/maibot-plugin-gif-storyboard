# GIF 动图分镜插件（maibot-plugin-gif-storyboard）

给 MaiBot（麦麦）补一块"动图视力"：**在 GIF 动图交给视觉模型之前，把动画的各个帧合成到同一张图上**，让视觉模型能看到动画的内容与时序——而不是只看到第一帧。

全部通过插件 SDK 实现，**不改宿主一行代码**。

## 为什么需要它

麦麦收到图片后会调用视觉模型（VLM）生成描述。VLM 链路是：

```
消息组件 binary_data ──► ImageManager.get_image_description(image_bytes)
                        ──► base64 + image_format ──► vlm.generate_response_for_image(...)
```

GIF 原样进入这条链路时，**大多数视觉模型对 `image/gif` 只取第一帧**：一个 20 帧的摔跤动图，麦麦眼里永远只有"开局那一瞬"。本插件在链路更早的位置把各帧拼成一张网格图（每帧带序号），VLM 看到的就变成了完整的"分镜表"。

## 工作原理

- 订阅宿主 `chat.receive.before_process` 钩子（消息进入处理链**之前**，允许改写）；
- 对消息里 `image` / `emoji` 组件的 `binary_data_base64` 检测 GIF 魔数（`GIF87a` / `GIF89a`）；
- 命中动图时用 Pillow 解帧 → **按时序均匀抽样**（默认最多 9 帧 = 3×3 网格）→ 拼成白底网格图（每帧左上角画序号）→ 原位替换二进制并写回新 hash；
- 宿主会用改写后的消息重建消息对象，其后的图片识别、描述缓存与图片落库**自动全部使用合成图**，无需任何额外接线。

```
适配器上报消息 ──► [本插件] GIF 帧合成替换 ──► 宿主消息处理 ──► VLM 识别（看到多帧）──► 描述入库
```

单帧 GIF（等价静态图）直接放行；解码失败、合成异常一律原样放行，绝不阻塞消息链。合成结果按「原图哈希 + 参数指纹」做内存缓存，同一个 GIF 反复刷屏也不会重复解码。

## 安装

```bash
cd /你的部署目录/plugins        # 例如 /opt/MaiBot/plugins
git clone <本仓库地址> maibot-plugin-gif-storyboard
# 重启麦麦（systemctl restart xxx / docker compose restart / 重启 bot.py）
```

> 目录名保持 `maibot-plugin-gif-storyboard`：插件配置存在插件目录内的 `config.toml`，换目录名会丢配置。

依赖只有 Pillow（`Pillow>=10.0.0`，见 requirements.txt；宿主环境一般已自带）。

重启后在 WebUI 插件页找到「GIF 动图帧合成（视觉增强）」确认已启用。所有配置项都在插件面板里，均有中文标签与说明，通常保持默认即可。

## 配置说明

### [merge] 帧合成

| 配置项 | 默认 | 说明 |
|---|---|---|
| 处理图片 | 开 | 处理普通图片组件（`type=image`）中的 GIF（群友发的 GIF 动图主要走这里） |
| 表情包策略 | **bypass** | 见下表，三种策略任选 |
| 最多帧数 | 9 | 超出上限的动画按时序均匀抽样（含首尾帧）；9 = 3×3 网格。帧越多信息越全，但图更大、token 更贵 |
| 最少帧数 | 2 | 帧数不足视为静态图，原样放行 |
| 绘制帧序号 | 开 | 每帧左上角标 1、2、3…，帮助 VLM 理解播放顺序 |

### 表情包策略怎么选

宿主表情链路"识别与存储共用同一个字节流"——直接替换表情二进制，`emoji_manager` 就会把合成图落盘表情库（`data/emoji`）并可能被收藏发出。因此提供三种策略：

| 策略 | 表情库存储 | VLM 识别 | 代价 |
|---|---|---|---|
| `bypass`（默认，推荐） | **原始 GIF**，收藏/发送完全保真 | 通过追加的合成图组件**看全多帧** | 表情 GIF 会多一次 VLM 调用（原图首帧 + 合成图各一次）；消息里多一个隐藏合成图组件 |
| `replace` | 合成图会进表情库、可能被收藏发出（观感是九宫格拼图），**原始 GIF 丢失** | 最直接 | 表情库污染 |
| `off` | 原始 GIF | 宿主原生行为（GIF 取首帧） | 识别退化 |

bypass 的效果：原表情组件原样保留，插件在其后追加一个 `content` 为空的 `image` 组件（携带合成网格图）。视觉链路照常走图片描述（落 `data/images`，不碰表情库），麦麦的上下文里会同时出现 `[表情包]` 与 `[图片: 动画各帧描述]`——既知道"这是个表情"，又知道动画内容。

## 只处理 GIF

插件只按文件头魔数（`GIF87a` / `GIF89a`）识别 GIF 动图：PNG / JPEG / WebP 等其他格式**零接触**；单帧 GIF 等价静态图，同样原样放行。

## 存储影响（重要）

| 存储位置 | 写入链路 | 默认行为 |
|---|---|---|
| `data/images`（图片识别缓存，Images 表 IMAGE 类型） | 图片组件（含 bypass 追加的合成图组件） | GIF 以合成网格图落库，仅作描述缓存用途，不会进入表情池 |
| `data/emoji`（表情库，Images 表 EMOJI 类型） | 表情包组件 | bypass / off 下**只落原始 GIF**，收藏与发送保真；`replace` 下会存进合成图 |

### [output] 输出图像

| 配置项 | 默认 | 说明 |
|---|---|---|
| 输出格式 | jpeg | jpeg 体积小省 token（推荐）；png 无损但明显更大 |
| JPEG 质量 | 85 | 50~95，仅 jpeg 生效 |
| 单帧格子边长上限 | 480 | 帧原图超过该尺寸等比缩小，控制合成图总体积 |
| 帧间隔（像素） | 4 | 网格帧之间的白色间隔 |

### [plugin]

| 配置项 | 默认 | 说明 |
|---|---|---|
| 插件总开关 | 开 | 关闭后 GIF 一律原样交给视觉模型 |

## 边界与说明

- **bypass 的 token 开销**：表情包 GIF 会产生两次识别（宿主对原图的首帧描述 + 插件合成图的多帧描述），表情包场景频率有限，通常可接受；介意可改 `off`。
- **合并转发里嵌套的图片暂不处理**：仅处理消息顶层组件。
- **不改动组件 `data` 字段**：宿主以 content 非空判定"已识别过"，本插件只动二进制与 hash，不会干扰识别流程。
- 典型开销：9 帧 480px 合成图 JPEG 约 100~300KB，单次合成毫秒级，缓存命中为零开销。

```bash
python self_test.py
```
